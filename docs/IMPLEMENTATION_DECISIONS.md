# Implementation Decisions

Decisions made where `docs/SPEC.md` is silent or incomplete. Append new entries; do not rewrite history without a reason.

## 2026-11-26 — Initial handoff

1. **Public-key distribution.** Every signed message envelope carries the author's public key. The being ID is derived from that key. Receivers verify the signature, derive the ID, and cache the key. This avoids a separate key-discovery protocol.
2. **Word list.** Use the BIP-39 English 2048-word list already in the repository.
3. **Emoji alphabet.** Use a fixed, versioned set of 256 common Unicode emoji. Exclude skin tones, flags, and ZWJ sequences for rendering consistency.
4. **Short identifier display.** Start at 4 words or 6 emoji. Extend one symbol at a time until unique in the current view.
5. **Search matching.** Case-insensitive substring match over the word sequence; exact substring match over emoji. Being and rendezvous search use the same rule.
6. **Time storage.** Unix milliseconds UTC. Normalize seconds to `00`. Display `HH:mm` in the viewer's local timezone. Show a day marker only when the rendezvous is not today.
7. **GOING display deduplication.** Group by channel and local `HH:mm`; deduplicate by being + channel + minute. Keep the newest signed claim if duplicates conflict.
8. **Incoming offer order.** Verified senders first, then unverified senders, then receipt time ascending.
9. **Image limits.** One image per offer. Maximum 25 MiB. Reject non-image MIME types and oversized files before offering.
10. **Audio UI.** Gentle pink progress bar with no numeric countdown. Mute and end controls always visible.
11. **Dedup cache TTL.** `PING`: 10 minutes. `GOING`: until scheduled time + 3 minutes + 5-minute margin. `SIGNAL`: 2 minutes.
12. **Seed implementation.** Prefer a maintained Node WebRTC library. If unreliable, run the seed as a headless browser peer. Keep the HTTPS bootstrap handshake minimal.
13. **Peer registry persistence.** IndexedDB; prune peers unreachable for 24 hours.
14. **Retry policy.** Exponential backoff with jitter. Never retry an unverified channel `SIGNAL`.
15. **Tests.** Vitest for unit/integration; Playwright for E2E. Use fake timers for presence and expiry. Use multiple browser contexts for WebRTC.
16. **Archive path.** `archive/` at the repository root, with a README stating that it is not built or tested.
17. **Strict future timestamps.** All messages with `created-at` later than the receiver's clock are rejected. No clock-skew allowance.
18. **Connection authorization.** A channel `SIGNAL` is accepted only from a locally verified being, only when the recipient is viewing that channel or has an active `GOING` announcement in it. Both sides must have verified each other for a connection to complete. The seed bootstrap is exempt.
19. **Media persistence.** A received image is saveable only while displayed. Dismissing removes the in-app copy. Saved downloads remain outside the app.
20. **Channel lifetime.** No automatic close. The channel screen remains until the user explicitly leaves.

## 2026-11-27 — Reference transport and implementation status

21. **Metadata/signalling transport.** The reference build uses a signed WebSocket relay for `PING`, `GOING`, and `SIGNAL`. Images and audio are direct WebRTC. A browser WebRTC mesh needs an out-of-band signalling substrate; the seed relay is that substrate. This is a deliberate reference-implementation compromise, not the final pure-peer topology in the spec.
22. **Peer connection cap.** A per-browser hard cap of 100 live WebRTC connections is implemented in `src/rdz/connection-budget.ts` and enforced by `RtcManager`. It does not limit the registry of known beings. The 20% refresh loop and WebRTC relay mesh are still not implemented because the reference transport has no mesh to rotate.
23. **Seed optionality.** `?seed=off` starts the app without a seed and uses cached state. Seedless first contact is explicitly out of scope per the 27 Nov 2026 decision.
24. **Seed bootstrap.** The first seed connection is a WebSocket upgrade, not a WebRTC offer/answer exchange. The seed is in-memory, has no being identity, and relays only signed metadata.
25. **Server-side signature verification.** The seed verifies every envelope before caching or routing it. This is stricter than the spec's untrusted-relay model; it protects the relay from malformed traffic and does not give it authority to create or alter messages.
26. **Archive.** Old circles, wall, voice notes, possession, package build, and their tests are under `archive/legacy/`. They are not built or tested.
27. **Public-key distribution.** Every envelope includes the author's public key. The seed and clients derive the being ID from it before accepting the message.
28. **No media persistence.** Incoming images live only in the browser while displayed. Dismissing revokes the object URL and removes the in-app copy. No wall or gallery exists.
29. **Test strategy.** Vitest covers IDs, signatures, expiry, relay-state aggregation, search, and timing. Playwright covers presence, channels, verification gates, image consent/save/dismiss/reuse/decline, audio consent/end, pinning, persistence, multiple simultaneous offers, `T + 3` expiry, and seed-off operation.

30. **Why a signed WebSocket relay.** WebRTC cannot begin without an out-of-band signalling exchange. A browser cannot accept an inbound socket, so a reachable bootstrap peer is required. WebSocket is used because it is reliable through proxies, available in browsers and Node, and needs no native WebRTC stack on the seed. Every relayed message is signed by its creator and verified by clients; the relay cannot forge or alter content.
31. **Why the first seed connection is not literally WebRTC.** WebRTC needs offer/answer/ICE before a peer connection exists. A seed can be a WebRTC data peer, but the browser still needs an HTTP/WebSocket signalling exchange to deliver the first offer and answer. The current reference build uses WebSocket for that exchange and for relayed messages. A WebRTC seed data channel is possible later with a Node WebRTC stack.

## 2026-11-27 — Multi-mask identity (spec requirement, implementation pending)

32. **Multiple masks, one active.** `docs/SPEC.md` now requires multiple masks per browser. Each mask owns its keypair, being ID, verification words, verified-being records, and pinned peer keys. Exactly one mask is active and online. Switching masks stops PING, closes the relay identity, tears down active image/audio sessions, reconnects as the new mask, and sends a fresh PING.
33. **Mask-local versus browser-level state.** Verification and pinned peers are mask-local. Pinned channels and local channel labels are browser-level preferences shared across masks. Existing `GOING` announcements are not retracted when the active mask changes.
34. **Migration.** Existing single-mask identity data migrates into the first mask. Removing a mask deletes its private key and verification state; signed messages already published remain valid.
35. **Implementation status.** The multi-mask story and functional requirements are in the spec, but the UI/store implementation is not yet updated for multiple masks.

## 2026-11-27 — FR-0 made primary

36. **WebRTC-exclusive application messages are now the primary transport invariant.** `PING`, `GOING`, and `SIGNAL` must travel only over WebRTC data channels. WebSocket/HTTPS is bootstrap-only: discovery and the first SDP/ICE exchange. The seed is a headless WebRTC peer: it may receive, cache, replay, and forward application messages only over WebRTC data channels, and it never accepts media.
37. **Peer-assisted signalling is mandatory.** Connected peers relay `SIGNAL` and peer introductions over WebRTC data channels. New peers use existing peers as introducers wherever possible.
38. **Current build non-compliance.** The committed reference build still relays `PING`, `GOING`, and `SIGNAL` over the seed WebSocket. This must be refactored before the transport can be called complete. The 100 live connection cap and direct WebRTC media path remain useful pieces of that refactor.

39. **Seed peer correction (27 Nov 2026).** The seed is a real headless WebRTC peer, not bootstrap-only. It may replay unexpired `PING`/`GOING` and forward `SIGNAL` over WebRTC data channels. It has no being identity and cannot receive images or audio. It still must never carry application messages over WebSocket or HTTP.

## 2026-11-27 — WebRTC mesh and multi-mask implementation

40. **WebRTC mesh.** Every peer opens a dedicated `rdz` data channel. Direct links are established with signed `SIGNAL` kinds `mesh-offer`, `mesh-answer`, and `mesh-ice`; connected peers forward ordinary `SIGNAL` flood-once over WebRTC. The same mesh carries `PING` and `GOING`. This supersedes decisions 21, 22, 30, 31, 35, and 38.
41. **Bootstrap-only WebSocket.** The browser WebSocket to `/signal` carries only `bootstrap-offer`, `bootstrap-answer`, and `bootstrap-ice`. The server rejects `PING`, `GOING`, and `SIGNAL` received over WebSocket. A Playwright test asserts that every WebSocket frame captured by the app is a bootstrap frame.
42. **Headless seed.** The seed is a `werift` `RTCPeerConnection` answerer. It verifies a signed challenge before binding a data channel to a being ID, then replays unexpired `PING`/`GOING` and forwards `SIGNAL` over WebRTC. It has no being identity and no media path.
43. **Mesh identity challenge.** On data-channel open the seed sends a fresh nonce. The client signs `rdz-mesh-hello:<nonce>` and returns its being ID and public key. The seed verifies the signature and derived ID before using the connection for routing. This is transport control, not an application message.
44. **Connection budget.** The 100 live WebRTC connection cap is shared by mesh links and media transfers through one `ConnectionBudget`. The seed link counts as one connection. Direct links use `mesh:<humanId>`; media uses its own transfer IDs.
45. **Peer rotation.** Every 4.5–5.5 minutes, if the budget is full and candidates exist, the browser drops up to 20% of non-priority direct links and replaces them with random registry candidates. Verified peers, the seed, and beings with active or pending media are never rotated. If the budget is not full, candidates are connected instead.
46. **Peer registry.** Being IDs and public keys learned from `PING`, `GOING`, or the seed are stored in IndexedDB and pruned after 24 hours. The registry is a reconnect aid; it cannot create a signalling path by itself.
47. **Shared `SIGNAL` path.** Media offers, answers, and ICE candidates use the same mesh and are forwarded by peers over WebRTC. Image and audio bytes remain on their own direct `RTCPeerConnection`.
48. **Multi-mask store.** IndexedDB schema v3 adds `masks`, `meta`, and `maskVerification` stores. The old single identity and verification records migrate into the first mask. Pins and channel labels remain browser-level.
49. **Mask switching.** Switching stops the mesh and RTC manager, clears the shared budget and all media state, reloads per-mask verification, starts a new mesh and RTC manager under the new key, and sends a fresh `PING`. Existing `GOING` envelopes remain cached and displayed. Other local masks are forced offline in the UI without retracting their signed announcements.
50. **Transport tests.** Playwright covers WebRTC-only application traffic, headless-seed health, and mask create/switch/persist/remove. Existing presence, image, audio, pinning, expiry, and multiple-offer tests now run over the WebRTC mesh.
51. **Cache TTL now follows validity.** The mesh and seed cache `PING` until its 5-minute presence window ends, `GOING` until scheduled time + 3 minutes, and `SIGNAL` for 2 minutes. This supersedes the 10-minute `PING` cache in decision 11.
52. **Self row in the landing online list.** The active mask is rendered only in the landing page's being list, marked `me · active mask` and `here now`. Its row opens the mask switcher instead of a verification dialog. It is filtered out of every rendezvous channel participant list, even when it has a `GOING` announcement there. It never offers `send photo` or `open voice`. Inactive local masks remain offline and hidden from the online list while their signed `GOING` announcements remain valid.
53. **Landing rendezvous emoji prefixes.** Channel cards use `uniqueEmojiDisplay` with a minimum of 3 emoji. The prefix is computed against every known rendezvous from `buildChannels` before the landing filter is applied, so filtering does not change it, and pinned-only rendezvous are included. A canonical rendezvous ID is 11 emoji, so 3–11 is the complete range. CSS permits wrapping rather than ellipsis so the full prefix is visible.
54. **Self label.** The active mask's landing row is marked `me · active mask`, not "you". It is excluded from rendezvous participant lists.
55. **Landing orbit restored.** The landing hero again uses the archived RDZ ellipse: a faint solid ellipse, an inset dashed ellipse, and one accent dot travelling the path in 26 seconds. It is decorative (`aria-hidden`), sits behind the hero content, is absent from channel screens, and is stopped by the existing reduced-motion rule.
56. **Full verification words are never clipped.** Modal elements using `.identity-words.full` override the compact chip's `nowrap`/ellipsis behaviour. They wrap and expose all 8 words. This applies to the mask switcher and the being verification dialog. The SIGNAL freshness test now pins its sample envelope to the captured `now` so a one-millisecond clock tick cannot make the fixture future-dated.
57. **Masthead restored.** The app again shows `rendezvous ✳ by [InstantHero mark]` above the top bar, using the archived InstantHero SVG (`src/ui/instanthero-mark.svg`) and the three-intersecting-lines RDZ mark. The same three-line mark replaces the old `◌` in the top-bar brand button. The masthead is decorative and does not capture input.
58. **Search icon.** The landing filter is wrapped in a positioned field with an inline SVG magnifying glass. The icon turns accent-coloured on focus and does not intercept input.
59. **Landing hero copy.** The hero heading is `The Internet is Here`, set larger than the previous headline. The old `Who is here now?` heading and explanatory lede are removed; the eyebrow and `Set a rendezvous` action remain.
60. **Being rows show their emoji prefix.** Landing and channel being rows now use a `minmax(54px, 9em)` emoji column and wrap rather than ellipsize. The display starts at the existing 6-emoji minimum and extends to the full 11 when needed, so a row never collapses to a single emoji plus an ellipsis.
61. **Own announcement confirmation.** A rendezvous channel shows a dedicated "your rendezvous" panel containing the active mask's live times. The participant groups still exclude the active mask, so setting a new time never produces an empty-screen message without confirming what was set. The panel disappears at `T + 3` like the announcement.
62. **Same-origin seed on every host.** `resolveBootstrapUrl` no longer falls back to `wss://randezvous.instanthero.ca/signal` for non-local hostnames. Without `VITE_SEED_URL` or `?seed=`, every host (LAN IP, HTTPS tunnel, production domain) uses its own same-origin `/signal`. This prevents a phone on a tunnel from joining the production seed while the desktop stays on the local seed.
63. **Secure-context gate.** `main.ts` checks `window.isSecureContext` and `crypto.subtle` before starting. Plain HTTP on a LAN IP now shows an explicit HTTPS-required screen instead of failing while creating a mask. Phone testing must use HTTPS or localhost.
64. **Mutual verification reminder.** The image-send dialog and README now state that both beings must verify each other before a media request can be delivered. Requests from an unverified being are still ignored by design.
65. **Full mask identifiers on small screens.** The mobile rule that hides the compact topbar identity words now targets only `.identity-chip`, so `.identity-words.full` inside dialogs stays visible. Every mask row shows its full 8-word and 11-emoji sequence, wrapping inside the scrollable dialog instead of using a truncated distinguishing prefix.
66. **Voice waits for microphone consent.** A voice request no longer expires while the other being is deciding or while either browser is showing a microphone permission prompt. The request panel stays up until someone accepts, declines, or ends it. The 30-second connection timeout starts only after the local microphone is ready and the offer/answer exchange is underway. A denied or failed microphone closes only that voice session and shows a toast instead of silently removing the panel, and a late microphone grant is stopped if its session was cancelled in the meantime.
67. **Bounded clock-skew tolerance.** `MAX_CLOCK_SKEW_MS` is one minute. Signed messages dated up to one minute ahead of the receiver's clock are accepted; farther-future messages are rejected. This supersedes decision 17. Phone and desktop clocks drift, and rejecting a signed accept or answer because it is seconds ahead stranded voice and image sessions. One minute covers ordinary network and time-sync effects while keeping the allowance small enough that a badly set clock cannot keep a message alive for long. The seed applies the same allowance.
68. **Interim voice acceptance.** The recipient sends `audio-accepting` immediately after choosing accept, before the browser microphone prompt opens. This clears the initiator's no-answer timer and moves the panel to connecting while the recipient grants permission. `audio-accept` is sent only after the recipient's stream is ready. Every wait is bounded: no answer within two minutes, no microphone completion within two minutes, and no connection within thirty seconds each close the session with a toast. Decision 66's no-timeout-while-prompting rule remains true because the acceptance signal stops the no-answer timer before the prompt.

## 2026-11-28 — Network traffic observability

69. **Landing traffic stream.** The landing hero carries a faded, live feed of the last nine mesh events on the right side of the orbit, behind the orbit line and fading toward the bottom. It shows limited detail: time, direction (`inbound`, `outbound`, `relaying`), envelope type, and a short peer or author label. The stream is a single button that opens a full-page view and remains available when the feed is empty.
70. **Traffic page scope.** The full page shows every event in a bounded 250-event session log, filterable by direction. Collapsed rows show the short author and routing summary; clicking a row reveals the full author and peer identifiers, created-at and observed-at times, byte size, rendezvous/time metadata, signal kind, target, destination count, and event sequence. The log is in memory only and clears on reload.
71. **No payload bodies.** Traffic rows never display envelope signatures, public keys, SDP, ICE candidates, media bytes, or other payload bodies. `SIGNAL` appears only as transport metadata with its kind and routing fields. It remains absent from being and rendezvous message surfaces; the traffic page is a local observability view, not a new application message type.
72. **Traffic instrumentation.** `MeshManager` reports a `coming` event once for each newly accepted inbound envelope, a `going` event for each locally signed publish with its destination count, and a `relaying` event whenever an accepted envelope is forwarded to at least one peer. Replay to a newly opened peer is tagged as `relaying` with a replay flag. Duplicate, invalid, and expired envelopes stay silent, matching FR-20's rule against error spam.
73. **Direction labels.** The traffic UI displays `coming` as **inbound** and `going` as **outbound**, so direction cannot be confused with the `GOING` rendezvous message type. Internal event names remain `coming`, `going`, and `relaying`.
74. **Masthead brand link.** The whole `rendezvous ✳ by [InstantHero mark]` masthead is an anchor to `https://instanthero.ca`, opened in a new tab so the current session stays intact. The link alone takes pointer events; the surrounding empty space remains inert. This supersedes the "does not capture input" clause of decision 57.

## 2026-11-28 — Image transfer robustness

75. **Ordered media negotiation.** SDP and ICE travel in separate signed envelopes and can arrive out of order after relay. Image and audio connections now buffer ICE candidates until the matching offer or answer has been applied instead of discarding them. This matters most when the phone is the offerer: dropping its candidates strands that direction even though the reverse direction succeeds. Duplicate offers or answers are ignored, and a failed `setRemoteDescription` closes only that transfer.
76. **Bounded image states.** An unanswered offer expires after two minutes. After consent, the connection must open and deliver metadata within thirty seconds, and the receiver aborts after thirty seconds without progress. The sender aborts if the whole transfer is not acknowledged within two minutes. Every failure sends `image-decline` with a reason and is shown on both sides; a stale offer can no longer leave either progress panel in `connecting` or `transferring` indefinitely.
77. **Mobile-safe image sending.** Image bytes use 16 KiB chunks and a receiver-controlled 256 KiB send window. The recipient acknowledges each 64 KiB it has accepted, so the sender never queues a whole 25 MiB image and does not depend on `RTCDataChannel.bufferedAmount` being updated synchronously. Older WebKit versions can under-report that value long enough to overflow SCTP and terminate the channel, which caused phone-to-desktop transfers to fail while the reverse direction succeeded. Peers that do not advertise flow control receive a conservative paced compatibility fallback. Send errors, channel errors, premature closes, and unreadable files are reported instead of escaping as unhandled errors, and the receiver still accepts Blob-delivered chunks defensively.
78. **Acknowledgement flush.** After receiving the last byte, the recipient queues the `ack` and keeps the peer connection open for one second before closing it, so the acknowledgement is not discarded with the transport. The sender no longer waits forever at 100%.
79. **Close-reason grace.** The receiver signs and relays its failure reason just before closing the transport, but the raw data-channel close reaches the sender first, so the sender used to report a generic "closed during the transfer" and mask the real cause (decision 76's "shown on both sides" did not hold for the sender). The sender now waits 1.5 s after a premature close for the peer's `image-decline` reason and only falls back to the generic message if none arrives. Offerer paths also guard re-entry (`startImageOffer` checks for a live pc; `startAudioOffer` sets a synchronous negotiating flag before `getUserMedia`), a duplicate answer that loses the race is treated as benign, and `sendImageBytes` surfaces a non-open channel instead of stalling silently.

## 2026-11-28 — Media notification cues

80. **Local notification cues.** The app synthesizes three short tones locally with the Web Audio API: a rising two-note cue when voice becomes live, a falling two-note cue when a live voice session ends, and a distinct three-note cue when an image offer or voice request arrives. They play once per transition or incoming request, reuse one audio context, require no downloaded audio or microphone stream, and degrade silently if the browser blocks audio playback. Incoming image offers share the request cue because they are the same user-facing consent event; the voice-request cue remains separate from start/end cues.

## 2026-11-28 — Protocol and media safety fixes

81. **Canonical identifier boundary.** Envelope verification accepts only canonical 15-character base64url encodings of 88-bit rendezvous, target, and channel identifiers. Transfer IDs are bounded URL-safe tokens. A malformed `GOING` is dropped instead of entering the board, seed cache, relay, or IndexedDB; poisoned rows from older builds are purged on load. Display helpers retain a raw-string fallback so no identifier can throw inside a render pass.
82. **One-week scheduling horizon.** A `GOING` may schedule at most seven days after its own signed `createdAt`. Browsers and the seed enforce the same rule before caching or replaying. The bound is relative to the signed creation time, so ordinary clock skew does not change it.
83. **Voice disconnect notices.** Both incoming and outgoing audio connection-state handlers announce "The voice connection was lost." before removing the live panel, satisfying FR-20/US-16 when the remote peer vanishes without sending `audio-end`.
84. **Signature-complete canonical JSON.** Canonicalisation builds null-prototype records, so a `__proto__` key remains an ordinary signed field instead of disappearing into the prototype setter. Relay-injected content now invalidates the signature.

## 2026-11-28 — Verified-only signalling and Being terminology

85. **Mask-local signalling privacy.** `verifiedOnlySignalling` is stored on each mask and defaults to `false`; older mask records are normalized in place without an IndexedDB schema change. The switch beneath the landing network traffic feed and the mask-switcher privacy card control the same accessible `role="switch"` state. The compact switch has no resting border or shadow; only its keyboard focus ring is outlined. When enabled, the mesh rejects unverified direct offers, closes existing unverified direct links, excludes them from rotation and sends, and drops `SIGNAL` traffic involving unverified beings. The headless seed remains exempt, and public `PING`/`GOING` discovery stays open. Verifying or unverifying a being reconciles the policy immediately.
86. **Being terminology.** Active UI copy, documentation, test names, TypeScript domain types, and CSS classes use **Being**. Wire and storage fields such as `humanId`, the `rdz-mesh-hello` payload, IndexedDB key paths, and the fixed BIP-39 word-list entry `human` remain unchanged for protocol and data compatibility. No signed envelope format or persisted identity changes.

## 2026-11-28 — Desktop received-photo surface

87. **Wide fine-pointer layout.** Received images use a dedicated `image-viewer` backdrop above the existing 820px breakpoint only when `(pointer: fine)` matches. Wide touch devices keep the scrollable modal. The desktop dialog is a viewport-height flex column: the image viewport takes the remaining space after the title, reminder, and actions, all of which are non-shrinking. This preserves the entire image and keeps save/dismiss visible even in short windows.
88. **Bounded decoding and resize.** A ResizeObserver on the image viewport decodes (or re-decodes) a fresh Blob copy of the received bytes at a device-pixel size bounded by the visible box, using successive halving for very large sources. The decoded bitmap is drawn to a temporary canvas so browsers without `URL.createObjectURL(ImageBitmap)` support receive a standard data URL; `object-fit: contain` supplies the final visual fit while intrinsic dimensions supply the aspect ratio. Decode results and observer work are coalesced; decode failures fall back to the original blob URL rather than dropping the photograph.
89. **Viewer scroll ownership.** Opening the viewer records the document scroll position and locks document scrolling while the desktop viewer is open, leaving the pinned dock fixed and avoiding a second scrollbar on the modal. Releasing the lock restores the previous scroll. Dismissal, channel exit, and mask switching all use one cleanup path for the object URL, decoded bitmap, observer, and scroll lock.

## 2026-11-28 — Photo transfer cancellation

90. **Explicit cancellation.** Every active photo progress row (waiting, connecting, or transferring) has a cancel button for both sender and recipient. Cancellation sends a signed `image-decline` with a side-specific reason, closes the direct connection, clears timers, and releases the connection-budget slot. The cancelling side sees "Image transfer cancelled." rather than a failure; the other side sees who cancelled. Incoming transports use the same 1.5 s close-reason grace as outgoing transports so the signed cancellation reason wins over the raw channel-close event.

## 2026-11-28 — Signalling encouragement copy

91. **Peer strength without private relay.** The note says **We encourage you to keep your public relay on to help the network stay connected and strong**. The **read why?** disclosure explains that each peer helps other beings find routes and makes the network resilient. It explicitly distinguishes public presence and connection requests from private content: photographs and voice never pass through another peer or the seed. This preserves the trust-versus-reachability explanation while removing any suggestion that being connected turns a browser into a personal-data relay.

## 2026-11-28 — Image-offer identity metadata

92. **Verification beside the sender ID.** Image and voice requests group the sender's word ID and verification status in one inline identity row so verification reads as a property of the being, not the media or duration. The image size or voice duration is a separate monospace line beneath it, with no verification text appended. The emoji ID remains above the identity row.

## 2026-11-28 — Mobile photo readability

93. **File-read fallback.** Selected photos and received Blob chunks use a shared reader that tries `Blob.arrayBuffer()` and falls back to `FileReader.readAsArrayBuffer()` when the native promise API is missing or rejects. This addresses mobile browsers that cannot read a selected photo through the native method even though the legacy reader still can. If both paths fail, the sender releases the transfer and both beings see an actionable retry message. Unit and Android-emulation regressions cover rejection, missing API support, cleanup, and successful delivery.
94. **Aspect-preserving desktop decode.** Received photos use their original intrinsic dimensions to calculate a bounded resize that fits the viewport without upscaling small images or changing the aspect ratio. Temporary decode output is capped at four million pixels, canvas failures fall back to the original Blob URL, and the source dimensions are retained across viewport resizes. The phone-to-desktop regression checks the decoded portrait aspect ratio, while a multi-chunk transfer exercises the original-Blob fallback when bitmap decoding rejects the source.

## 2026-11-28 — Channel time actions

95. **Separate immediate joining from scheduling.** The channel header always exposes **add a time**, which opens the existing picker. When no other being has an active announcement, the empty-state message itself is a button with **join now** underneath it. **Join now** signs and publishes a `GOING` for the current minute, normalized to zero seconds, without opening the picker. The empty-state action depends on other beings' announcements, not on whether the active mask has already announced.

## 2026-11-28 — Android sender file access

96. **Eager photo snapshot and layered readers.** The sender starts reading a selected photo immediately after local validation, while the Android file-picker grant is still fresh, and retains the resulting bytes while waiting for consent. No bytes are sent before consent. If `Blob.arrayBuffer()` and `FileReader.readAsArrayBuffer()` both reject a provider-backed File, the shared reader tries `Blob.stream()` and then a temporary Blob URL fetched locally; every object URL is revoked. An unreadable selection withdraws the offer immediately instead of waiting for the desktop recipient to accept. Unit and Android-emulation regressions cover the eager read, stream fallback, Blob-URL cleanup, and complete read failure.
